# ISE Certificate-Based Authentication + Server-Cert Verification

**Date:** 2026-07-14
**Status:** Approved (design)

## Problem

The MCP server connects to Cisco ISE APIs using Basic auth over TLS, and TLS
peer verification is hard-disabled in `clients/tls.py` (`CERT_NONE`,
`check_hostname=False`). Two gaps:

1. No support for **client-certificate-based authentication**, which ISE
   supports as an alternative to Basic auth. Per the Cisco guide, the client
   presents a cert and ISE authenticates the API user from it — no
   `Authorization` header is sent:

   ```
   curl -X GET https://10.127.96.218/ers/config/op/systemconfig/iseversion \
     --cert apiuser-combined.pem -H "Accept: application/json"
   ```

2. **Server-certificate verification is disabled**, so the channel is
   encrypted but the ISE server is not authenticated — an on-path attacker can
   MITM and capture credentials. We want verification ON by default, with an
   opt-out for testing.

## Decisions (from brainstorming)

- **Cert is standalone auth.** When a client cert is configured, present it at
  the TLS layer AND send NO `Authorization` header. ISE authenticates by cert.
  Basic-auth paths are used only when no cert is configured.
- **Server verification default ON, opt-out toggle.** Enabled by default;
  `ISE_VERIFY_SERVER_CERT=false` disables it for testing. This is a **breaking
  change** for existing deployments connecting by IP to self-signed/internal-CA
  ISE — documented as such.
- **Separate cert + key, optional passphrase.** Distinct `ISE_CLIENT_CERT` and
  `ISE_CLIENT_KEY` paths, plus optional `ISE_CLIENT_KEY_PASSWORD` for encrypted
  keys.
- **CA bundle + independent hostname toggle.** `ISE_CA_BUNDLE` supplies a
  CA/self-signed cert to trust; `ISE_VERIFY_HOSTNAME` independently controls
  hostname/SAN matching so operators can verify the chain but skip hostname
  matching when connecting to a bare IP whose cert has no IP SAN.

## Architecture

All four HTTP clients already funnel their SSL context through the single
`clients.tls.build_ssl_context()` function:

- `clients/client_factory.py` — autogenerated OpenAPI `AuthenticatedClient`s
- `clients/mnt_client.py` — MnT Basic-auth XML client
- `clients/ise_web_session.py` — `/admin/*` cookie/form-login client

Because the client certificate lives at the TLS layer, loading it in
`build_ssl_context()` gives **mTLS transport to every client for free**. Auth
path selection (whether to send an `Authorization` header) is handled
separately in the two API-auth surfaces (`client_factory`, `mnt_client`).

Insertion points: `clients/settings.py` (config), `clients/tls.py` (TLS
context), `clients/client_factory.py` and `clients/mnt_client.py` (auth-path
selection).

## Section 1 — Settings (`clients/settings.py`)

Six new optional fields, `SecretStr` where sensitive:

| Field | Env var | Default | Purpose |
|---|---|---|---|
| `ise_client_cert` | `ISE_CLIENT_CERT` | `None` | Path to client cert PEM |
| `ise_client_key` | `ISE_CLIENT_KEY` | `None` | Path to client private-key PEM |
| `ise_client_key_password` | `ISE_CLIENT_KEY_PASSWORD` | `None` (`SecretStr`) | Passphrase for encrypted key |
| `ise_verify_server_cert` | `ISE_VERIFY_SERVER_CERT` | `True` | Peer cert chain verification (opt-out) |
| `ise_verify_hostname` | `ISE_VERIFY_HOSTNAME` | `True` | Hostname/SAN check (independent toggle) |
| `ise_ca_bundle` | `ISE_CA_BUNDLE` | `None` | Path to CA/self-signed cert to trust |

Empty-string env values are treated as absent (extend the existing
`_empty_str_to_default` validator for the new string/path fields, consistent
with current handling).

Cross-field validation (fail at **startup**, not first request):

- `ise_client_cert` and `ise_client_key` must be set together — one without the
  other is a config error.
- `ise_verify_hostname=True` combined with `ise_verify_server_cert=False` is
  invalid (stdlib `ssl` forbids `check_hostname=True` with `CERT_NONE`) —
  reject with a clear message.
- Every referenced file (`ise_client_cert`, `ise_client_key`, `ise_ca_bundle`)
  must exist and be readable — fail loud at startup with the offending path.

A convenience predicate `client_cert_configured` (True when both cert and key
are set) is exposed for the auth-path selectors.

## Section 2 — TLS context (`clients/tls.py`)

`build_ssl_context()` becomes config-driven; the hard-coded `CERT_NONE` is
removed:

```
ctx = SSLContext(PROTOCOL_TLS_CLIENT)
ctx.minimum_version = TLSv1_2                      # unchanged

if settings.ise_verify_server_cert:
    ctx.verify_mode = CERT_REQUIRED
    ctx.check_hostname = settings.ise_verify_hostname
    if settings.ise_ca_bundle:
        ctx.load_verify_locations(settings.ise_ca_bundle)
    else:
        ctx.load_default_certs()                   # system trust store
else:
    ctx.check_hostname = False                     # MUST precede CERT_NONE
    ctx.verify_mode = CERT_NONE

if settings.client_cert_configured:                # mTLS — applies to ALL clients
    ctx.load_cert_chain(
        certfile=settings.ise_client_cert,
        keyfile=settings.ise_client_key,
        password=<passphrase.get_secret_value() or None>,
    )
```

The existing once-per-process posture log (`_TLS_POSTURE_LOGGED`) is retained
with a richer message: verify on/off, hostname on/off, client-cert present/absent.
The module docstring's "verification intentionally disabled" residual-risk note
is replaced to describe the new default-ON posture and the opt-out.

## Section 3 — Auth-path selection (cert = standalone)

New precedence, extending the existing idiom in both `client_factory.get_client`
and `mnt_client._resolve_per_call_auth`:

1. Per-user `X-ISE-Authorization` header present → use it (unchanged, wins).
2. **Client cert configured → cert mode: attach NO `Authorization` header.**
   ISE authenticates via the cert already loaded in the shared TLS context.
3. `require_per_user_credential=True` → raise `MissingIseCredentialError`
   (unchanged).
4. SA creds present → Basic fallback (unchanged).
5. None of the above → raise `MissingServiceAccountError` (unchanged).

Client-specific mechanics:

- **OpenAPI clients** (`client_factory._create_client`): the autogenerated
  `AuthenticatedClient` unconditionally writes `Authorization: <prefix> <token>`
  when it lazily builds its own httpx client (see
  `get_async_httpx_client`/`get_httpx_client`). To send NO auth header in cert
  mode, construct an `httpx.AsyncClient` ourselves (base_url, timeout,
  `verify=context`, `follow_redirects=False`) and attach it via
  `set_async_httpx_client()` (and `set_httpx_client()` for the sync path),
  which bypasses the header-writing branch. **Cached per `ClientName`** like the
  service-account path (not built-fresh like the per-user path): the client cert
  is a single, process-wide config, so there is no per-user token to leak and no
  unbounded cache growth — the concerns that justify not caching the per-user
  path do not apply here. Basic and per-user paths keep using `prefix`/`token`
  as today.
- **MnT** (`mnt_client._resolve_per_call_auth`): cert mode returns
  `{"auth": _NoOpAuth()}` with no `Authorization` header, so the client-level
  `BasicAuth` (if any) cannot overwrite it. The `_NoOpAuth` flow already exists
  for exactly this "neutralise client-level auth for one call" purpose.
- **Web session** (`/admin/*`): out of scope for auth changes — it is a
  cookie/form-login surface, not an ERS/OpenAPI auth surface. It still gets the
  client cert in the shared TLS context (mTLS transport) but its cookie/form
  auth flow is unchanged.

## Section 4 — Docs, tests, error handling

- **`.env.example`**: document all six new vars, with a security note that
  `ISE_VERIFY_SERVER_CERT` now defaults to `true` (breaking for setups relying
  on the old disabled default) and guidance on `ISE_CA_BUNDLE` /
  `ISE_VERIFY_HOSTNAME` for internal-CA / bare-IP deployments.
- **README**: a "Certificate-based authentication" section mirroring the curl
  example, plus the verification/CA-bundle/hostname toggles and their defaults.
- **Tests**:
  - `test_tls.py`: verify ON (`CERT_REQUIRED`, hostname follows toggle), verify
    OFF (`CERT_NONE`, hostname forced off), CA bundle load, client-cert load
    (incl. passphrase), and the illegal `hostname=True + verify=False` combo
    surfaced as a settings error. Generate throwaway certs/keys under
    `tmp_path`.
  - `test_client_factory.py`: cert mode emits NO `Authorization` header;
    per-user header still wins over cert mode; Basic fallback unchanged when no
    cert configured.
  - `test_mnt_client.py`: cert mode sends no `Authorization` header and
    neutralises client-level BasicAuth via `_NoOpAuth`; per-user precedence
    intact.
  - Settings tests: cert-without-key (and vice versa), missing/unreadable file
    paths, and the illegal toggle combo all fail at startup with actionable
    messages.
- **Error handling**: file-not-found, bad passphrase (`ssl.SSLError` from
  `load_cert_chain`), and illegal toggle combinations fail at startup with
  messages naming the offending env var / path.

## Out of scope

- Changing the web-session (`/admin/*`) auth flow.
- Per-user client certs (cert is a single server-wide config, like the SA creds).
- Regenerating or forking the autogenerated OpenAPI client code.
