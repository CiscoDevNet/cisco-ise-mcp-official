# Creating a New Tool

How to add an MCP tool to this server. Read
[Development](../README.md#development) in the README first for dev setup and the
test command.

A tool is worth adding when it answers a question an ISE operator actually asks
and no existing tool answers it. Check
[MCP_TOOLS_CATALOG.md](MCP_TOOLS_CATALOG.md) before you start, and consider
opening a
[new tool request](https://github.com/CiscoDevNet/cisco-ise-mcp-official/issues/new/choose)
first so the shape can be agreed before you write code.

## Placeholders in this guide

Code examples are generic. Substitute consistently — the same placeholder means
the same thing everywhere:

| Placeholder | Means | Example |
|-------------|-------|---------|
| `<domain>` / `<Domain>` | The tool's domain, in file/class case | `policy` / `Policy` |
| `<noun>` / `<Noun>` / `<nouns>` | The thing returned, singular and plural | `policy_set` / `PolicySet` / `policy_sets` |
| `<verb>` | The action, for the tool name | `search`, `diagnose`, `investigate` |
| `<method_name>` / `<MethodName>` | The handler method, snake and Pascal case | `search_policy_sets` / `SearchPolicySets` |
| `<param>` | A tool parameter | `name_contains` |
| `<SURFACE>` / `<Surface>` | An OpenAPI client surface | `POLICY` / `Policy` |
| `<iseOperationName>` | The ISE operation, as ISE names it | `getPolicySets` |

So a tool named `ise_<verb>_<noun>` lives in `server.py`, delegates to
`<domain>_tool_handler.<method_name>()` in `tools/<domain>_tool_handler.py`, and
returns a `<Noun>SearchResult` from `models/<domain>_models.py`.

## How a tool call flows

```
MCP client (Claude Code, Cursor, ...)
  |
  v  streamable-HTTP
FastMCP server                     server.py
  |  IseCredentialMiddleware       utils/ise_credential_middleware.py
  |  (lifts X-ISE-Authorization into a ContextVar)
  v
@ise_mcp_server.tool function      server.py
  |  thin: no logic, delegates, returns a typed model
  v
<Domain>ToolHandler method         tools/<domain>_tool_handler.py
  |  validate -> call ISE -> filter -> truncate -> build model
  |
  +--> utils/input_validators.py         reject bad input before any ISE call
  +--> BaseToolHandler.execute_api_call  tools/base_tool_handler.py
  |      -> ClientFactory.get_client()   clients/client_factory.py
  |         -> autogenerated_api_clients/<pkg>/api/<tag>/<op>.asyncio_detailed
  +--> MNTClient.get() / .get_stream()   clients/mnt_client.py   (MnT XML APIs)
  |      guarded by MntGate.guard()      clients/mnt_gate.py     (-> ISE_BUSY)
  +--> services/<name>_resolver.py       cross-source enrichment
  v
models/<domain>_models.py          IseResultModel subclass
  |  becomes the tool's outputSchema + structuredContent
  v
MCP client
```

## Which layer does what

| Path | Responsibility |
|------|----------------|
| `server.py` | Tool registration, schemas, docstrings, handler singletons, lifespan |
| `tools/` | Handler classes — validation, ISE calls, filtering, truncation, model assembly |
| `services/` | Resolvers that enrich or derive across data sources (policy, latency, failure, diagnostics) |
| `clients/` | Transport and auth: `ClientFactory`, `MNTClient`, `MntGate`, `ISESettings`, TLS |
| `models/` | Pydantic result models (the wire contract) and the error contract |
| `utils/` | Input validators, XML parsing, sampling notes, credential middleware |
| `resources/` | Per-tool domain glossaries served over `ise://glossary/tool/{tool_name}` |
| `autogenerated_api_clients/` | Generated OpenAPI clients — checked in, never hand-edited |

## Before you start: which ISE API backs the tool?

This determines how much work it is.

| Situation | What you need |
|-----------|---------------|
| An operation on an already-generated OpenAPI surface (`endpoints`, `policy`, `deployment`, `certificates`, `patch_and_upgrade`) | Steps 1-7 |
| A **new** ISE OpenAPI surface | [Adding a new OpenAPI surface](#adding-a-new-openapi-surface) first, then steps 1-7 |
| The MnT (Monitoring & Troubleshooting) API | Steps 1-7, but see [MnT-backed tools](#mnt-backed-tools) — MnT is XML, not OpenAPI, and is rate-gated |
| No ISE API exposes the data | That is an upstream ISE limitation, not something this server can work around. |

## Step 1 — Define the result model

Add to `models/<domain>_models.py`. Every model **must** subclass
`IseResultModel` from [`models/base.py`](../models/base.py), which strips `None`
fields from the serialized payload so "absent when …" field descriptions stay
true.

```python
class <Noun>Summary(IseResultModel):
    name: str = Field(..., description="<The identifier an agent will cite.>")
    <numeric_field>: int = Field(..., ge=0, description="<What it measures.>")
    status: Literal["<ok>", "<warning>", "<bad>"] = Field(
        ..., description="<Derived verdict>"
    )

    @classmethod
    def from_api(cls, raw: dict) -> "<Noun>Summary":
        """Map ISE's camelCase response onto the model."""
        return cls(name=raw["<iseFieldName>"], ...)


class <Noun>SearchResult(IseResultModel):
    <nouns>: list[<Noun>Summary] = Field(..., description="<Matches, capped by limit.>")
    total_count: int = Field(..., ge=0, description="Total matches before truncation.")
    count: int = Field(..., ge=0, description="Number of items returned.")
    has_more: bool = Field(..., description="True when total_count exceeds count.")
```

Conventions:

- Every field carries `Field(..., description=...)`. The description is part of
  the `outputSchema` an agent reads — write it for that audience.
- `Literal[...]` for enumerated verdicts and statuses, never bare `str`.
- `@classmethod from_api(cls, raw: dict)` for camelCase-to-snake_case mapping;
  `@classmethod from_nodes(...)`-style constructors for derived summaries.
- The top-level envelope carries either `total_count` / `count` / `has_more`
  (the policy models' convention) or `total_matching_sessions` / `sample_size` /
  `sampling_note` (the session models' convention). Follow whichever sibling
  tools in your domain use.

> **Note:** Never add a return annotation to a `model_serializer`. Annotating it
> collapses the derived JSON Schema to a bare `{"type": "object"}` and destroys
> the `outputSchema` FastMCP advertises. `models/base.py` documents this.

## Step 2 — Validate every input

Reuse what exists in [`utils/input_validators.py`](../utils/input_validators.py)
before writing anything new — `validate_limit`, `validate_minutes`,
`validate_hostname`, `validate_mac_address`, `validate_ip_address`,
`validate_username`, `validate_name_substring` and friends already cover most
parameters.

A new validator returns the normalized value or raises:

```python
def validate_<param>(value: int) -> int:
    """Validate that *<param>* is within [<min>, <max>]."""
    if value < <min> or value > <max>:
        raise_tool_error(
            ErrorCategory.CLIENT_ERROR,
            "INVALID_<PARAM>",
            f"<param> must be between <min> and <max>, got {value}.",
        )
    return value
```

The message is shown to the agent and the user, so make it actionable and state
the accepted range.

## Step 3 — Write the handler method

Handlers live in `tools/<domain>_tool_handler.py` as `<Domain>ToolHandler`. For
an OpenAPI-backed tool, subclass
[`BaseToolHandler`](../tools/base_tool_handler.py):

```python
class <Domain>ToolHandler(BaseToolHandler):
    _ISE_PAGE_SIZE = 100
    _MAX_PAGES = 3

    def __init__(self, client_factory: ClientFactory, ...):
        super().__init__(ClientName.<SURFACE>, client_factory)
```

`execute_api_call` is the only place that talks to a generated client, and it
owns all HTTP/JSON/TLS error mapping — do not wrap it in your own try/except:

```python
raw_response = await self.execute_api_call(
    api_function=<generated_operation>.asyncio_detailed,
    operation_name="<iseOperationName>",
    page=page,
    size=self._ISE_PAGE_SIZE,
)
```

Always use the generated `asyncio_detailed` variant; `execute_api_call` parses
`response.content` itself and bypasses the generated `parsed` field.

Then follow this order inside the method — the sequence matters:

1. **Validate and normalize every parameter first**, so bad input raises before
   any ISE call is made. Tests assert this.
2. `logger.info("<Doing the thing>", **validated_params)`.
3. Call ISE via `execute_api_call`.
4. Unwrap the payload guarded by a type check — most ISE endpoints return
   `{"response": [...]}`, but some return a bare JSON array:
   ```python
   items = raw_response.get("response", []) if isinstance(raw_response, dict) else raw_response
   ```
5. Filter client-side, count the **full** match total, then slice to `limit`.
6. Build the models, set the envelope counters, and call
   `build_sampling_note(...)` from [`utils/sampling.py`](../utils/sampling.py) —
   it returns `None` when nothing was truncated, so `IseResultModel` drops the
   field.
7. `logger.info("... complete", ...)` and return the model.

Give any fan-out a module- or class-private cap, following the existing
`_MAX_PAGES`, `_MAX_FAN_OUT_POLICY_SETS`, `_MAX_PSN_NODES`, `ENRICHMENT_CAP`
constants. Every one of those is load on a production ISE deployment.

### Errors

The whole error contract is [`models/error_models.py`](../models/error_models.py):
`raise_tool_error(category, code, message, *, retry=False)` raises a FastMCP
`ToolError` carrying a JSON `ToolErrorDetail`, which the client sees as
`isError=True`.

| Category | Use for | Existing codes |
|----------|---------|----------------|
| `CLIENT_ERROR` | Bad tool input | `INVALID_LIMIT`, `INVALID_MINUTES`, `INVALID_HOSTNAME`, `INVALID_MAC_ADDRESS`, `MISSING_IDENTIFIER`, … |
| `EXTERNAL_ERROR` | ISE misbehaved or is unreachable | `ISE_UNREACHABLE` (retry), `ISE_TLS_VERIFICATION_FAILED`, `ISE_API_ERROR` (retry iff 5xx), `ISE_INVALID_RESPONSE`, `ISE_BUSY` (retry) |
| `SERVER_ERROR` | A bug or enrichment failure on our side | `INTERNAL_ERROR`, `POLICY_ENRICHMENT_ERROR`, `LATENCY_ENRICHMENT_ERROR`, `FAILURE_ENRICHMENT_ERROR` |

Reuse an existing code rather than inventing a near-duplicate. Set `retry=True`
only when retrying could actually succeed.


### Logging

`from logger import logger`, then structured key-value calls:
`logger.info("Message", key=value)`. `DEBUG_MCP=true` enables debug level.

**Never log credential values, and never log raw ISE response bodies** — an ISE
error body can quote the request URL and the `Authorization` header value.
Log presence, codes, and counts.

## Step 4 — Add a resolver, if the tool crosses data sources

Only if the tool combines sources (OpenAPI + MnT, or an API + node logs). Add
`services/<name>_resolver.py` with constructor-injected dependencies and one
`async def resolve(...)`. Isolate per-item failures so one bad node does not fail
the call, and raise a `<X>_ENRICHMENT_ERROR` under
`ErrorCategory.SERVER_ERROR` if the whole resolution is impossible.
`services/deployment_diagnostics_resolver.py` is a good model.

## Step 5 — Register the tool in `server.py`

Three edits, in this order:

1. Import the handler and result model at the top.
2. Instantiate the handler singleton in the module-scope block after
   `ise_mcp_server = FastMCP(...)`.
3. Add the tool function.

If the tool needs long-lived setup or teardown, wire it into `app_lifespan`.

> **Note:** Do not make network calls at startup. `app_lifespan` runs outside any
> inbound MCP request, so no per-user `X-ISE-Authorization` header is in scope and
> the call can only use the service account — which fails in header-only
> deployments. Build anything that needs an ISE fetch lazily on first use, as
> `FailureToolHandler._get_failure_resolver` does.

The tool function itself:

```python
@ise_mcp_server.tool(annotations={"readOnlyHint": True, "openWorldHint": True})
@measure_time_async
@normalize_docstring
async def ise_<verb>_<noun>(
    <param>: Annotated[Optional[str], "<What it filters, and how it matches.>"] = None,
    minutes: Annotated[int, Field(ge=0, le=1440, description="Lookback minutes.")] = 60,
    limit: Annotated[int, Field(ge=1, le=50, description="Max results.")] = 25,
) -> <Noun>SearchResult:
    """
    <One sentence: what this returns, with CAPS on the discriminating noun.>

    USE THIS for: <the operator questions it answers>.

    Do NOT use for: <the neighboring case>, use `<sibling_tool>` instead.

    Returns:
    - <nouns>[]: <the fields an agent can cite.>
    - summary: <derived counts and verdict.>
    """
    result: <Noun>SearchResult = await <domain>_tool_handler.<method_name>(
        <param>=<param>,
        minutes=minutes,
        limit=limit,
    )
    return result
```


## Step 6 — Add the tool glossary

Add an entry to `TOOL_GLOSSARIES` in
[`resources/ise_glossary.py`](../resources/ise_glossary.py), composing existing
section strings:

```python
TOOL_GLOSSARIES: dict[str, str] = {
    ...
    "ise_<verb>_<noun>": _compose(<DOMAIN>_GLOSSARY, <RELATED>_GLOSSARY),
}
```

The `ise://glossary/tool/{tool_name}` resource picks it up with no other change.
Add the tool name to `EXPECTED_TOOL_NAMES` in `tests/test_ise_glossary.py`.

## Step 7 — Tests

Tests live flat in `tests/` as `test_<module>.py`. There is no `asyncio_mode`
configured, so every async test needs an explicit marker. Per-file boilerplate:

```python
PROJECT_DIR = Path(__file__).resolve().parent.parent
if str(PROJECT_DIR) not in sys.path:
    sys.path.insert(0, str(PROJECT_DIR))

pytest_plugins = ("pytest_asyncio",)
```

**Handler tests** (`tests/test_<domain>_tool_handler.py`) mock the seam directly
below the handler and assert on the exact parameters sent to ISE:

```python
class Test<MethodName>:
    @pytest.mark.asyncio
    async def test_<expected_behavior>(self):
        handler = _make_handler()          # MagicMock factory, never a real client
        with patch.object(handler, "execute_api_call", new_callable=AsyncMock) as mock_exec:
            mock_exec.return_value = {"response": [_raw_<noun>("<value>")]}
            result = await handler.<method_name>(<param>="<value>")

        assert result.count == 1
        assert mock_exec.call_args[1]["size"] == 100

    @pytest.mark.asyncio
    async def test_invalid_limit_raises_before_api_call(self):
        handler = _make_handler()
        with patch.object(handler, "execute_api_call", new_callable=AsyncMock) as mock_exec:
            with pytest.raises(ToolError):
                await handler.<method_name>(limit=9999)
        mock_exec.assert_not_called()      # validation must precede the ISE call
```

**Tool tests** (`tests/test_server.py`) patch the handler singleton by name and
import the tool inside the test so the patch is active:

```python
with patch("server.<domain>_tool_handler") as mock_handler:
    from server import ise_<verb>_<noun>
    ...
    assert mock_handler.<method_name>.call_args[1]["limit"] == 25   # pin defaults
    assert isinstance(result, <Noun>SearchResult)
    to_jsonable_python(result)                                     # wire shape
```

Cover at minimum: the happy path, an empty ISE response, each validator
rejecting before any ISE call, truncation and the sampling note, and error
propagation. Assert error codes by parsing the payload:

```python
data = json.loads(str(exc_info.value))
assert data["error_code"] == "ISE_UNREACHABLE"
```

`tests/test_server.py` maintains `sys.modules` stubs for `fastmcp` and the
generated clients, used when the real packages cannot import. If your handler
imports a new generated API module, add it to the stub map.

## Step 8 — Document the tool

[MCP_TOOLS_CATALOG.md](MCP_TOOLS_CATALOG.md) is the tool reference, and a new
tool is not done until it is in there. Add a `### <exact_tool_name>` entry under
the right `##` category, matching the existing entries:

- Description: what it returns, cost and latency notes, cross-links to sibling
  tools. Add a `**Heavy MnT call**` note if it is gated.
- `**Questions this tool answers:**` — 10-15 bullets of verbatim end-user
  phrasing with realistic values. These are what make the tool discoverable.
- The parameter table: `| Parameter | Type | Required | Default | Description |`.
- `**Returns:**` field bullets, a fenced `json` example response, and a
  truncated-sample example if the tool samples.
- `**Use when:**` / `**Do not use when:**` / `**Best practices:**` bullets. Each
  "do not use" bullet should name the correct alternative tool.

Then add rows to the `## Tool Selection Guide` and `## Data Sources` tables at
the end of the catalog, and to the Table of Contents if you added a category.


## MnT-backed tools

The MnT API is not OpenAPI-generated. Handlers take `mnt_client` directly and use
`MNTClient.get()` or `.get_stream()`, parsing XML through `utils/xml_parser.py`.
`SessionToolHandler` and `FailureToolHandler` are the two examples.

Heavy MnT reads must go through the gate:

```python
async with self.gate.guard():
    ...
```

`MntGate` is admission control plus a circuit breaker; when it refuses, the
caller gets a retryable `ISE_BUSY`.

## Adding a new OpenAPI surface

Only needed if your tool reaches an ISE API area that has no generated client
yet. A tool over an already-generated surface (`endpoints`, `policy`,
`deployment`, `certificates`, `patch_and_upgrade`) skips this section entirely.

ISE OpenAPI endpoints are consumed through typed clients generated from OpenAPI
specs, rather than hand-written HTTP calls. The moving parts:

| Path | Purpose |
|------|---------|
| `api_specs/*.yaml` \| `*.json` | OpenAPI specs (one per API area, e.g. `policy-bundled.yaml`) |
| `api_client_config/*.yaml` | [`openapi-python-client`](https://github.com/openapi-generators/openapi-python-client) generator config (package name, version, options) |
| `autogenerated_api_clients/` | Generated client packages — **checked in**, but treated as generated output |
| `scripts/generate_api_clients.sh` | Regenerates every enabled client |

### Preparing a spec

Specs are sourced from the official
[Cisco ISE API framework](https://developer.cisco.com/docs/identity-services-engine/latest/cisco-ise-api-framework/),
then trimmed to the operations the server actually calls and placed under
`api_specs/`. If a source spec uses external `$ref`s, bundle it into a single
self-contained file first — see [api_specs/README.md](../api_specs/README.md) for
the Redocly bundling steps.

### Generator config

Each client needs a generator config under `api_client_config/` that sets the
package name, version, and options. Use the existing
[`api_client_config/policy.yaml`](../api_client_config/policy.yaml) as a
template. `package_name_override` becomes the directory name under
`autogenerated_api_clients/`.

### Generating the clients

Each client is produced by an `openapi-python-client generate` invocation. Add a
block for your new client to
[`scripts/generate_api_clients.sh`](../scripts/generate_api_clients.sh),
following the existing policy block, so it is regenerated with the rest:

```bash
uv run openapi-python-client generate \
  --path api_specs/<name>.yaml \
  --config api_client_config/<name>.yaml \
  --output-path ./autogenerated_api_clients/ \
  --overwrite
```

Then regenerate all enabled clients by running the script:

```bash
./scripts/generate_api_clients.sh
```

Commit the resulting package. `autogenerated_api_clients/` is checked in but
treated as generated output — never hand-edit it.

### Registering the client

The generator produces the package; the factory decides how it authenticates and
where it points. Add a `ClientName` enum member and a `_client_registry` entry in
[`clients/client_factory.py`](../clients/client_factory.py):

```python
ClientName.<SURFACE>: ClientRegistryEntry(<Surface>Client, f"{ISE_OPEN_API_BASE_PATH}/<path>"),
```

Import the generated client as
`from autogenerated_api_clients.<pkg>.client import AuthenticatedClient as <Surface>Client`.


### New env vars

Add them to `ISESettings` in [`clients/settings.py`](../clients/settings.py) with
a `validation_alias="ISE_..."`, include the field in the `_empty_str_to_default`
validator list, then mirror them in `.env.example` and the
[Configuration](../README.md#configuration) table in the README.
